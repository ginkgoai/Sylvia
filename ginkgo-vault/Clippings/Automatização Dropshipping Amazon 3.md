## 2\. CSV é ótimo para validação, mas fraco para crescimento

Para uma pessoa e poucos pedidos, CSV é suficiente. Para escala previsível, ele começa a criar problemas:

- bloqueio quando aberto no Excel;
- consultas cada vez mais lentas;
- inexistência de índices;
- baixa segurança transacional;
- dificuldade de conciliar eventos concorrentes;
- migrações de esquema trabalhosas;
- Git crescendo a cada alteração.

O próprio projeto já precisou implementar escrita atômica e avisos contra arquivo aberto no Excel.

### Melhor evolução enxuta

Não migraria diretamente para PostgreSQL. Isso seria instalar um reator nuclear para ligar uma lâmpada.

Usaria:

```
Agora: SQLite em modo WAL
Depois: PostgreSQL
Exportação: CSV/XLSX
Auditoria: tabela append-only
```

SQLite mantém o modelo local, não exige servidor e oferece:

- transações;
- índices;
- consultas rápidas;
- integridade referencial;
- backups simples;
- migração futura direta.

Os CSV podem continuar existindo como exportação e portabilidade, mas não como fonte primária.

## 2\. Integração Amazon

A integração deve ser feita pela SP-API, sem scraping do Seller Central.

### Pedidos

A versão atual da Orders API é `v2026-01-01`. Ela permite buscar informações de pedidos de forma seletiva e substitui progressivamente os endpoints antigos. Para acessar informações de destinatário e outros dados restritos, ainda é necessário possuir as funções apropriadas. [^4]

Fluxo:

```
Amazon detecta pedido
        ↓
Order ingest
        ↓
Ledger event
        ↓
Cálculo de margem
        ↓
Ficha de compra
        ↓
Aprovação humana
```

A Amazon também fornece notificações `ORDER_CHANGE` para mudanças de status e solicitações de cancelamento. As notificações podem ser entregues por SQS ou EventBridge. [^5]

### Limitação do modelo local

Um aplicativo exclusivamente em localhost não recebe EventBridge/SQS sozinho.

Duas alternativas:

1. Polling controlado da Orders API a cada poucos minutos.
2. Um relay mínimo em nuvem que recebe o evento e o entrega ao painel local.

Para o MVP, polling é mais simples. Para escala, relay.

### Taxas

O parâmetro de comissão está atualmente pendente e bloqueia o cálculo completo.

Não preencheria isso manualmente por categoria como solução definitiva. Usaria a **Product Fees API**, que fornece taxas estimadas por produto e preço. [^6]

O sistema deve armazenar:

```
fee_snapshot
fee_source
fee_retrieved_at
fee_expiration
```

Assim, a margem deixa de ser “30% baseada numa tabela” e passa a ser “30% baseada numa estimativa de taxas obtida às 14h32”.

### Preços

A Product Pricing API oferece informações de ofertas e preços competitivos e é desenhada para suportar repricers. A operação `getCompetitiveSummary` passou a retornar ofertas de menor preço e preços de referência. [^7]

O sistema pode recomendar:

```
Preço atual: R$ 149,90
Concorrente: R$ 144,90
Preço mínimo sustentável: R$ 139,43
Preço recomendado: R$ 143,90
Impacto esperado: margem 32,8%
```

Mas a alteração deve permanecer como rascunho até aprovação.

### Anúncios

A Listings Items API e a Product Type Definitions API podem criar e atualizar ofertas e validar os atributos exigidos por tipo de produto. Atualizações completas precisam de cautela, porque atributos omitidos podem ser removidos. [^8]

No primeiro estágio:

- operar apenas ASINs já existentes;
- criar rascunho de oferta;
- validar elegibilidade;
- calcular taxas;
- aprovar preço;
- humano confirma publicação.

## Motor de matching de produtos

O matching atual é funcional, mas ainda depende demais de título e da avaliação do modelo.

A versão robusta deve usar uma cascata:

```
1. GTIN / EAN / UPC exato
2. Marca + MPN/modelo
3. Características estruturadas
4. Variação, quantidade e dimensões
5. Similaridade textual
6. Similaridade visual
7. Veredito Claude com evidência
```

Exemplo:

```

Motivo: potência, portas e modelo divergentes
```

## Economia unitária

A fórmula atual está bem centralizada no código.

Mas faltam três conceitos operacionais.

## 1\. Custo normal versus custo promocional

```
custo_base
custo_promocional
cupom
frete
validade_promocao
```

Um candidato não deveria ser aprovado estruturalmente se só dá lucro com um cupom pontual.

Classificação:

```
Margem sem cupom ≥ mínima → saudável
Margem só fecha com cupom → oportunístico
Margem não fecha → rejeitado
```

## 2\. Margem estimada versus realizada

```
margem_projetada
margem_na_compra
margem_final
erro_de_previsao
```

O sistema então aprende onde perde dinheiro:

```
estimou 36%
comprou com 31%
finalizou com 24%
desvio: -12 pontos
```

## 3\. Reserva de devolução e tributação

Atualmente imposto e reserva de devolução estão configurados em zero porque foram informados dessa forma.

Isso é uma premissa operacional, não uma validação contábil. Antes de usar o painel como fonte de lucro líquido real, esses componentes precisam ser confirmados com histórico e orientação contábil.

## Limite obrigatório: sem cloaking

Não entraremos no produto com:

- cloaker para mostrar conteúdo diferente ao revisor;
- VPN ou proxy para disfarçar país, identidade ou conta;
- rotação de contas para fugir de restrições;
- manipulação de fingerprint;
- alteração de arquivos para evitar detecção;
- republicação automática de anúncios rejeitados.

Meta considera evasão do processo de revisão um motivo para restrições, enquanto o TikTok proíbe explicitamente tentativas de contornar ou interferir em seus processos de moderação. [^13]

Entram, de forma legítima:

- infraestrutura e armazenamento regionais;
- landing pages localizadas por país;
- segmentação geográfica oficial;
- CDN e processamento próximo ao mercado;
- remoção de EXIF, GPS e identificadores de dispositivo por privacidade;
- normalização técnica de áudio e vídeo;
- verificador de políticas antes da publicação;
- detecção de claims arriscados;
- análise de rejeição e geração de nova versão compatível;
- fluxo de recurso e revisão manual.

A limpeza de metadados será **higiene de privacidade**, não camuflagem.

## Monetização recomendada

Não cobraria uma porcentagem do “lucro líquido da empresa”. Isso gera conflitos sobre impostos, despesas, devoluções, folha e outros custos que o sistema não controla.

Cobraria sobre a **margem de contribuição verificada e atribuída à plataforma**:

```
Receita liquidada
− taxas Amazon
− custo do produto
− frete
− devoluções
− impostos configurados
− gasto de anúncios atribuído
= margem de contribuição verificada
```

Hipótese inicial:

| Plano | Assinatura | Variável |
| --- | --- | --- |
| Core | R$ 497/mês | consumo excedente |
| Growth | R$ 997/mês | 3% da margem atribuída |
| Scale | R$ 1.997+/mês | 1,5%–2,5% negociado |

A porcentagem só seria aplicada aos pedidos e campanhas efetivamente administrados ou influenciados pelo sistema, sempre com relatório de reconciliação.

Stripe Billing pode cuidar da assinatura, consumo e itens variáveis de fatura. Como os pagamentos das vendas ocorrem na Amazon, a taxa de performance deve ser faturada após a reconciliação; não é possível simplesmente descontá-la diretamente dos repasses da Amazon por meio do Stripe. Stripe Connect oferece application fees quando a plataforma participa do fluxo de pagamento, o que não é o caso padrão aqui. [^15]
