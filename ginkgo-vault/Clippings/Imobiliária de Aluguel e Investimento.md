Você **não está longe tecnologicamente** de uma primeira oferta inspirada na EliseAI.

O erro é achar que a EliseAI é essencialmente um chatbot mais inteligente.

Ela é isto:

> **Um sistema operacional imobiliário vertical, com IA na interface e workflows determinísticos por trás.**

Hoje, o Leaf/Callima já possui a “boca e parte do cérebro”:

- WhatsApp;
- texto, áudio, imagem e documentos;
- RAG;
- qualificação;
- agenda;
- follow-up;
- handoff humano;
- CRM e histórico;
- execução por ferramentas;
- base multi-tenant.

O que falta é o **sistema nervoso imobiliário**: entidades, estados, regras, integrações, métricas, confiabilidade e um fluxo completo que termine em resultado financeiro.

---

## 1\. O que a EliseAI realmente vende

A EliseAI centraliza locação, comunicação, visitas, manutenção, renovação, inadimplência e relatórios em um CRM especializado chamado EliseCRM. Ela trabalha por voz, SMS, e-mail e webchat, sincronizando dados com sistemas imobiliários existentes. [^1]

A arquitetura conceitual é:

```
Canais de comunicação
        ↓
Identificação do prospecto ou morador
        ↓
CRM imobiliário central
        ↓
IA vertical especializada
        ↓
Workflow operacional
        ↓
Ação real no PMS, agenda, cobrança ou manutenção
        ↓
Métrica financeira
```

Não é:

```
Mensagem → LLM → resposta bonita
```

É:

```
Mensagem
→ identificar pessoa e imóvel
→ entender estágio do relacionamento
→ consultar dados confiáveis
→ tomar uma ação permitida
→ atualizar o sistema
→ criar tarefa
→ acompanhar resultado
→ medir conversão
```

Essa diferença parece pequena na tela, mas é a distância entre um bot de demonstração e uma empresa de bilhões.

## 2\. As camadas de produto da EliseAI

## Prospect Management

A IA atende leads, recomenda imóveis, qualifica interessados, agenda visitas e executa follow-ups. A empresa afirma automatizar mais de 90% das conversas e agendamentos de visitas nesse módulo. Também mantém uma única conversa por prospecto, mesmo quando ele pesquisa múltiplos imóveis. [^2]

Isso exige:

- inventário disponível em tempo real;
- preferências estruturadas;
- regras de qualificação;
- agenda dos corretores;
- histórico único do cliente;
- pipeline de locação;
- follow-up automático;
- definição do próximo melhor passo.

## Resident Operations

Depois da assinatura, a IA não desaparece. Ela passa a atender o morador:

- dúvidas;
- segunda via;
- mudança;
- manutenção;
- pagamentos;
- renovação;
- encerramento de contrato.

Essa continuidade é uma das maiores vantagens da EliseAI: o mesmo relacionamento acompanha a pessoa durante todo o ciclo imobiliário. [^1]

## Manutenção

A EliseAI coleta detalhes do problema, categoriza a solicitação, identifica urgência, cria a ordem de serviço, encaminha ao responsável e mantém o morador atualizado. Ela também oferece troubleshooting antes de deslocar um técnico. [^3]

Exemplo:

```
“Meu chuveiro não esquenta.”

→ identificar imóvel e unidade
→ perguntar desde quando
→ verificar disjuntor
→ classificar urgência
→ sugerir teste seguro
→ criar ordem de serviço
→ definir prioridade
→ atribuir técnico
→ avisar morador
→ acompanhar resolução
```

A Callima hoje provavelmente consegue conversar sobre isso. O que falta é **controlar o processo inteiro**.

## Inadimplência

A EliseAI envia lembretes, explica valores, apresenta opções de pagamento, acompanha acordos e inclui fiadores quando necessário. As conversas continuam no mesmo histórico do morador. [^4]

O diferencial não é “mandar cobrança”.

É manter um estado operacional:

```
Em dia
→ vencimento próximo
→ vencido
→ primeiro contato
→ promessa de pagamento
→ acordo ativo
→ acordo descumprido
→ escalação humana/jurídica
→ regularizado
```

## Voz

O VoiceAI atende e realiza chamadas para locação, manutenção, renovação, inadimplência e dúvidas gerais. Registra transcrição, intenção, dados do prospecto e resultado no CRM; quando não resolve, transfere ou cria uma tarefa humana. [^5]

Isso confirma uma decisão correta da sua arquitetura:

- ElevenLabs pode fornecer a experiência de voz;
- Workforce controla regras, ferramentas e permissões;
- Leaf registra a operação;
- Callima conduz a conversa.

## Integrações

A EliseAI conecta-se a sistemas imobiliários como Yardi, Entrata, RealPage, ResMan e AppFolio, além de ferramentas de acesso, visitas e marketplaces. A empresa também mantém equipes próprias de soluções, suporte e implantação. [^6]

Aqui está uma das maiores diferenças para o Leaf:

> A EliseAI entra dentro da operação existente. O Leaf ainda tende a exigir que a operação se adapte a ele.

## 7\. Features obrigatórias do primeiro produto

## 7.1 Identidade única

Um lead não pode aparecer como cinco pessoas porque falou por números ou canais diferentes.

Entidade:

```
Pessoa
├── telefones
├── e-mails
├── documentos
├── canais
├── conversas
├── preferências
├── visitas
├── propostas
└── contratos
```

## 7.2 Inventário estruturado

Cada unidade precisa ter:

- código;
- imóvel;
- endereço;
- bairro;
- preço;
- condomínio;
- IPTU;
- taxas;
- quartos;
- banheiros;
- garagem;
- área;
- mobiliado;
- pets;
- disponibilidade;
- fotos;
- regras;
- diferenciais;
- status.

A IA nunca deve inventar preço ou disponibilidade.

Esses dados precisam vir de uma fonte de verdade.

## 7.3 Recomendador de imóveis

A Callima deve transformar linguagem em filtros:

> “Quero algo perto da PUC, até R$ 2.800 com condomínio, uma vaga e que aceite gato.”

Estrutura:

```json
{
  "location": ["Jardim das Américas", "Guabirotuba"],
  "maximum_total_cost": 2800,
  "parking_spaces": 1,
  "pets": true,
  "bedrooms_minimum": 1
}
```

Depois:

- busca estruturada;
- ranking;
- justificativa;
- alternativas;
- registro de preferências.

RAG não deve ser usado para encontrar disponibilidade. Isso é consulta estruturada no banco.

## 7.4 Qualificação configurável

Cada imobiliária define:

- renda mínima;
- tipo de garantia;
- restrições;
- ocupantes;
- pets;
- data prevista;
- finalidade;
- documentos necessários.

A EliseAI permite configurar perguntas, critérios e objetivos diferentes por empreendimento. [^2]

O Leaf precisa de “modos” equivalentes:

- modo visita;
- modo qualificação;
- modo aplicação;
- modo recuperação de lead.

## 7.5 Agenda transacional

Não basta “ver horário”.

Precisa:

- consultar disponibilidade;
- bloquear horário;
- impedir conflito;
- atribuir corretor;
- associar imóvel;
- confirmar presença;
- lembrar prospecto;
- permitir reagendamento;
- registrar no CRM;
- acompanhar no-show.

## 7.6 Follow-up orientado a estado

Não use delays soltos no n8n.

Use uma máquina de estados:

```
Novo lead
→ contato iniciado
→ qualificado
→ imóveis enviados
→ visita sugerida
→ visita marcada
→ visita realizada
→ proposta solicitada
→ entregue ao humano
→ ganho/perdido
```

Cada estado define:

- mensagem permitida;
- próxima ação;
- prazo;
- condição de saída;
- responsável;
- limite de tentativas.

## 7.7 Handoff confiável

Ao transferir:

- a IA deve parar imediatamente;
- o humano recebe um resumo;
- motivo da transferência;
- imóveis discutidos;
- preferências;
- objeções;
- próxima ação recomendada.

Depois, o humano pode devolver o controle à IA explicitamente.

## 7.8 Painel de operação

Telas mínimas:

1. Inbox.
2. Leads.
3. Imóveis.
4. Agenda.
5. Pipeline.
6. Tarefas.
7. Conhecimento.

## 9\. Bugs que precisam virar prioridade absoluta

## P0 — riscos que impedem vender

### Mensagem duplicada

Causa comum:

- webhook repetido;
- retry de provedor;
- worker executando duas vezes.

Correção:

- idempotency key;
- event ledger;
- deduplicação por message ID;
- operações transacionais.

### Visita duplicada

A IA não pode confirmar dois horários porque duas tool calls rodaram juntas.

Correção:

- lock de agenda;
- unique constraint;
- reserva temporária;
- confirmação transacional.

### Informação inventada

Nunca permitir que o modelo invente:

- preço;
- disponibilidade;
- taxa;
- metragem;
- endereço;
- condição contratual.

Correção:

- dados financeiros e disponibilidade apenas via tool;
- respostas estruturadas;
- campo `source`;
- bloqueio quando a consulta falhar.

### Vazamento entre clientes

Nenhuma conversa, documento ou imóvel pode atravessar tenants.

Correção:

- `tenant_id` obrigatório;
- RLS;
- testes de isolamento;
- namespaces separados;
- autorização no serviço, não apenas na interface.

### IA falando durante atendimento humano

Correção:

```
conversation_control:
  AI_ACTIVE
  HUMAN_ACTIVE
  PAUSED
  CLOSED
```

Toda mensagem de saída precisa verificar esse estado.

### Follow-up infinito

Correção:

- limite por campanha;
- janela de silêncio;
- opt-out;
- cancelamento quando houver resposta;
- encerramento por estado.

### Tool call executada duas vezes

Exemplos:

- dois agendamentos;
- dois e-mails;
- duas cobranças.

Correção:

- action ID;
- idempotência;
- outbox;
- retry seguro.

### Contexto desatualizado

O imóvel foi alugado, mas continua sendo oferecido.

Correção:

- sincronização incremental;
- timestamps;
- invalidação de cache;
- verificação final antes de agendar ou propor.

## 11\. Camada de confiabilidade necessária

Antes de novas features, implemente:

## Audit Stream

Cada ação precisa registrar:

```
Quem iniciou
Qual agente decidiu
Qual versão do prompt
Qual modelo
Quais dados foram consultados
Qual ferramenta foi executada
Qual foi o resultado
Qual foi o custo
Qual foi a latência

```

## Testes de conversação

Crie uma suíte com cenários fixos:

- lead normal;
- lead sem renda;
- imóvel indisponível;
- tentativa de negociação;
- cliente agressivo;
- emergência;
- áudio incompreensível;
- pedido fora da política;
- conflito de agenda;
- handoff;
- retorno após vários dias.

Cada nova versão deve rodar contra esses casos.

## Shadow Mode

A nova Callima responde internamente, mas a resposta não é enviada.

Compare:

- versão atual;
- nova versão;
- resposta humana;
- resultado esperado.

## Canary

Libere uma versão nova para:

- uma imobiliária;
- parte das conversas;
- um tipo de intenção.

Não altere todos os clientes ao mesmo tempo.

A EliseAI também enfatiza onboarding com integração, configuração, conhecimento, usuários, treinamento, testes e go-live — não apenas conectar um número de telefone. [^1]

## Os problemas reais encontrados no Leaf

## P0 — o motor Callima ainda é específico de cliente

O workflow versionado ainda usa:

```
path: prv-webhook
```

Isso mostra que o motor produtivo não foi completamente convertido em template multi-tenant.

Além disso, o agrupamento Redis usa uma chave baseada apenas no número:

```
NUMERO_LEAD_CALLIMA
```

Não aparece `org_id` nessa chave.

Em ambiente multi-tenant, o formato correto seria algo como:

```
leaf:{org_id}:conversation:{channel}:{remote_jid}:buffer
```

Sem isso, duas organizações atendendo o mesmo número podem disputar contexto.

### Prioridade

1. resolver organização pela instância;
2. inserir `org_id` em todas as chaves;
3. remover nomes de clientes;
4. remover identificadores de credenciais do workflow exportado;
5. criar template neutro;
6. publicar por ambiente.

---

## P0 — falhas sem retry seguro

A documentação registra que, quando uma ação falha depois de ser reivindicada pelo consumer, ela pode permanecer aprovada e marcada como capturada, sem nova tentativa automática.

Isso precisa virar uma máquina de estados:

```
pending
→ approved
→ processing
→ sent

processing
→ failed
→ retry_scheduled
→ processing

failed
→ dead_letter
```

Cada ação precisa de:

- `idempotency_key`;
- contador de tentativas;
- próxima tentativa;
- último erro;
- timeout de processamento;
- dead-letter queue;
- reprocessamento manual.

---

## P0 — script de produção quebrado

A API possui:

```json
"build": "tsc",
"start": "node dist/server.js"
```

Mas o entrypoint é `index.ts`, e o TypeScript está configurado para preservar a estrutura em `dist`. Não existe `server.ts`.

O start deveria provavelmente ser:

```json
"start": "node dist/index.js"
```

Isso precisa ser confirmado no pipeline, mas é um bug objetivo do estado atual.

---

## P0 — autenticação com legado confuso

O entrypoint ainda registra `@fastify/jwt` com fallback:

```
super-secret-dev-key-change-in-production
```

ao mesmo tempo em que a arquitetura já migrou para Supabase GoTrue.

Mesmo que o JWT legado não esteja no caminho principal, ele deveria ser:

- removido;
- ou explicitamente isolado;
- e nunca possuir segredo padrão permissivo.

Código de segurança ambíguo vira uma porta que ninguém lembra se está trancada.

- **Callima Studio:** tom, regras, perguntas e permissões.
- **Tarefas:** pendências humanas.
- **Relatórios:** conversão, tempo de resposta e desempenho.
- **Equipe:** corretores e gestores.
- **Integrações:** WhatsApp, calendário e sistemas imobiliários.
- **Configurações:** unidades, horários, limites e políticas.

A interface não deve mostrar “workflow n8n”, “modelo LLM” ou “BullMQ”.

Ela deve dizer:

- Automação ativa.
- Integração saudável.
- Última sincronização.
- Três ações falharam.
- Callima transferiu cinco atendimentos.
- Dois imóveis estão com disponibilidade desatualizada.

- CRM;

## Hermes, LiteLLM e OpenRouter

Esses três componentes não são iguais.

Se forem usados sem separação clara, viram três cérebros tentando dirigir o mesmo corpo.

## OpenRouter

É a camada de acesso aos modelos externos.

Serve para:

- escolher provedores;
- usar vários modelos;
- evitar dependência de uma única empresa;
- comparar custo e qualidade;
- acessar modelos diferentes por tarefa.

## LiteLLM

Deve ser o **gateway interno de modelos**.

Tudo chama LiteLLM, não OpenRouter diretamente.

Responsabilidades:

- padronizar chamadas;
- selecionar modelo;
- fallback;
- limites por organização;
- custos;
- observabilidade;
- rate limiting;
- logs;
- roteamento.

Exemplo:

```
Callima conversa simples
→ modelo rápido e barato

Análise documental
→ modelo com contexto maior

Classificação de intenção
→ modelo pequeno estruturado

Situação complexa
→ modelo mais robusto
```

## Hermes

Deve ser o runtime de raciocínio e ferramentas.

Responsabilidades:

- montar contexto;
- selecionar ferramentas;
- aplicar políticas;
- controlar passos;
- interpretar resultado;
- decidir se responde ou transfere;
- produzir saída estruturada.

A hierarquia correta:

```
Callima = identidade e comportamento
Hermes = runtime do agente
LiteLLM = gateway de modelos
OpenRouter = fornecedor de modelos
```

## n8n e fluxos variáveis

O maior erro seria criar uma cópia gigantesca do workflow para cada imobiliária.

## Modelo correto

Criar um catálogo de workflows genéricos:

```
WF-001 — Entrada de mensagem
WF-002 — Handoff humano
WF-003 — Agendamento de visita
WF-004 — Reagendamento
WF-005 — Lembrete de visita
WF-006 — Follow-up pós-visita
WF-007 — Sincronização de imóveis
WF-008 — Importação de planilha
WF-009 — Envio de mídia
WF-010 — Recuperação de erro
```

Cada organização possui configurações:

```json
{
  "org_id": "org_123",
  "workflow": "WF-003",
  "enabled": true,
  "config": {
    "calendar_provider": "google",
    "confirmation_hours_before": 24,
    "reminder_hours_before": 2,
    "assign_strategy": "round_robin"
  }
}
```

O workflow é o mesmo.

Os dados e regras variam por organização.

## O que não deve ficar no n8n

- estado principal do lead;
- disponibilidade oficial;
- permissões;
- regras de negócio críticas;
- cálculo financeiro;
- identidade do tenant;
- verdade sobre visitas;
- controle de duplicidade.

Essas coisas pertencem ao Leaf API e ao PostgreSQL.

O n8n executa. Não governa.

## Fluxo completo de uma mensagem

```
1. Cliente envia WhatsApp
2. Evolution recebe
3. Leaf Ingress valida o webhook
4. Mensagem é deduplicada
5. Evento é gravado no PostgreSQL
6. Job entra no BullMQ
7. Worker carrega:
   - organização
   - lead
   - conversa
   - estado
   - configuração da Callima
8. Hermes interpreta a intenção
9. Hermes consulta LiteLLM
10. LiteLLM escolhe modelo via OpenRouter
11. Callima pede uma ferramenta
12. Leaf API valida permissão
13. Serviço imobiliário executa
14. Se necessário, n8n/API/MCP é acionado
15. Resultado volta ao Hermes
16. Resposta é gravada
17. Job de envio é criado
18. Evolution envia a resposta
19. Chatwoot recebe o espelho
20. Dashboard atualiza métricas
```

Tudo deve carregar:

```
org_id
conversation_id
correlation_id
actor
source
timestamp
```

## Infraestrutura VPS inicial

Para pilotos, ainda faz sentido usar uma VPS única com Docker Compose.

Como Chatwoot, n8n, PostgreSQL, Redis e Evolution estarão juntos, eu trataria:

- **16 GB de RAM como mínimo funcional** para poucos clientes;
- **32 GB como configuração mais segura**;
- armazenamento NVMe;
- backups externos;
- monitoramento de disco;
- volumes persistentes;
- restore testado.

Os modelos permanecem externos via OpenRouter, então a VPS não precisa carregar GPU.

## Evolução

```
Fase 1
Uma VPS Docker Compose

Fase 2
VPS de aplicação + VPS de dados

Fase 3
Workers separados por carga

Fase 4
Banco gerenciado e filas gerenciadas

Fase 5
Orquestração maior apenas se o volume justificar
```

Não há motivo para Kubernetes agora. Seria comprar um aeroporto antes de ter três aviões.
